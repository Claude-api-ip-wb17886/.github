<p>Claude API住宅代理IP配了却不通、或者时好时坏，是故障排查里很常见的一类。故障分析从现象往回走：先说清到底是不通、慢、还是反复验证，再按层级往回查。现象分不清，排查就会在几个方向之间来回摇摆。</p>

<p>排查顺序是分层：配置层、出口层、账号层，再加本地层。配置层看你填的对象对不对，出口层看资源本身，账号层看历史与环境，本地层看代理设置和插件。从最容易验证的一层查起，成本最低也最快。</p>

<p>很多人一不通就怀疑出口，其实本地层更该先看：系统代理设置是否冲突、浏览器或运行环境有没有多余插件、本机时间是否准确。这些看似不起眼的东西，恰恰是很多不通的真正来源。先把它们排掉，再往外查。</p>

<p>配置层看的是：请求是否真的指向了代理端、填写的连接信息有没有错、转发协议是否匹配环境。配置写错一个字段，表现就是不通或反复验证。把配置和准备阶段记下的出口信息逐项比对，错误往往就藏在其中。</p>

<p>出口层看资源本身：注册归属是否被标异常、是否落在预期地区、最近是否变化过。用公开数据库查一次归属，再实际连一次让对方回显地区，三者对照。若彼此矛盾，问题大概率在出口这一层。</p>

<p>怎么判断问题是不是代理引起的？用前后对比：连之前记下当前出口，连之后再查一次，看是否按预期变化；同时观察不通的现象是否随之出现或消失。若代理一开就出问题、一关就恢复，嫌疑就落在配置或出口上。</p>

<p>若配置和出口都正常，就回到账号层。账户历史、登录设备、操作节奏留下的痕迹，换代理也解决不了。把这一层纳入视野，是为了避免在代理上反复折腾却毫无进展。很多时候，真正的变量藏在这里。</p>

<p>排查时最要紧的纪律是一次只改一项。把设备、协议、地区一起改，结果好了也说不清是哪一步起作用，下次还是抓瞎。拆开改、每步记，看似慢，其实是最短的路。这条纪律在代理故障里尤其重要。</p>
